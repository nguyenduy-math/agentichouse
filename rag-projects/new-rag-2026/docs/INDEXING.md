# Document Indexing Pipeline

This document traces what happens to a file from the moment it is uploaded until the knowledge graph is ready for queries.

---

## Overview

```
Upload (PDF/DOCX/TXT)
        │
        ▼  document_parser.py   (parse pages, NFC-normalize)
        ▼  text_splitter.py     (article-aware chunking → ≤2800 chars)
        │
   graphrag_workspace/input/*.txt   (one .txt file per chunk)
        │
        ▼  graphrag index       (entity/relation extraction, community detection, embedding)
        │
   graphrag_workspace/output/*.parquet   (entities, relationships, text_units, communities, …)
        │
        ▼  import_to_neo4j.py   (bulk MERGE into Neo4j)
        │
   Neo4j (Entity, Community, TextUnit nodes + vector indexes)
        │
        ▼  GraphRAGService.reload()   (DataFrames loaded into memory)
        │
   Ready for queries
```

State machine inside `IndexingService`: `idle → indexing → importing → ready | error`

---

## Stage 1 — Document Upload and Pre-processing

**Endpoint:** `POST /api/v1/admin/ingest`  
**Code:** [admin.py](backend/app/routers/admin.py), [indexing_service.py](backend/app/services/indexing_service.py)

1. The raw file (PDF, DOCX, or TXT) is saved to `backend/data/documents/`.
2. `IndexingService.prepare_for_graphrag()` is called in a thread pool.

### 1a. Parsing (`document_parser.py`)

| Format | Primary parser | Fallback |
|--------|---------------|---------|
| PDF | `pdfplumber` (handles multi-column, tables) | `pymupdf` (scanned/protected PDFs) |
| DOCX | `python-docx` (paragraphs + table cells) | — |
| TXT | `pathlib.read_text` | — |

All extracted text is **NFC-normalized** (`unicodedata.normalize("NFC", ...)`) to ensure consistent Vietnamese diacritic representation across sources.

### 1b. Chunking (`text_splitter.py`)

A three-tier strategy respects the document's own structure before falling back to fixed-size splitting:

**Tier 1 — Vietnamese article boundaries** (`Điều N.`)  
If the text contains Vietnamese article markers, split at each `Điều N.` header. Overflow segments (> 2800 chars) fall through to Tier 3.

**Tier 2 — Section markers** (`=== SECTION ===`)  
If the text has explicit section markers but no `Điều` headers, split there.

**Tier 3 — Fixed-size sliding window**  
Chunk size: 2800 chars, overlap: 400 chars (≈ 2800 / 7).  
Chunk boundaries are snapped to the nearest sentence end (`.\n`, `\n\n`, `. `) only if the break point is past the halfway mark of the chunk, preventing mid-sentence cuts.

Each chunk is written as a separate `.txt` file:
```
graphrag_workspace/input/<stem>_part0000.txt
graphrag_workspace/input/<stem>_part0001.txt
...
```

## Stage 2 — GraphRAG Indexing

**Endpoint:** `POST /api/v1/admin/index`  
**Code:** [indexing_service.py](backend/app/services/indexing_service.py) → `_run_graphrag_index()`  
**Config:** [graphrag_workspace/settings.yaml](backend/graphrag_workspace/settings.yaml)

The indexing service runs `graphrag index --root graphrag_workspace/` as a subprocess. Microsoft GraphRAG 2.x executes the following internally:

### 2a. Chunking (GraphRAG level)

GraphRAG applies a second chunking pass on each `.txt` input file:
- Chunk size: **1200 tokens**, overlap: **100 tokens**
- Group by: `id` (one logical document = one pre-split `.txt` file)

Because each input file was already split to ≤ 2800 chars in Stage 1, GraphRAG rarely needs to split further. The two-level split ensures both structure-awareness (Stage 1) and token-level safety (Stage 2).

### 2b. Entity and Relationship Extraction

For each text chunk, the LLM (Gemini `gemini-2.5-flash`) is prompted with a Vietnamese template (`prompts/entity_extraction.txt`) to extract:

**Entity types:**
- `tổ chức` (organization)
- `người` (person / role)
- `địa điểm` (location)
- `sự kiện` (event)
- `khái niệm` (concept)
- `quy trình` (process)
- `chính sách` (policy)

Each entity gets a name, type, and description. `max_gleanings: 1` means GraphRAG makes one follow-up extraction pass to catch missed entities.

Relationships (typed edges between entity pairs) are extracted in the same pass. Entity descriptions are then **embedded** with `gemini-embedding-001` (3072-dim vectors stored in LanceDB during indexing).

### 2c. Description Summarization

When multiple chunks mention the same entity, GraphRAG merges and summarizes the descriptions using the LLM (`prompts/summarize_descriptions.txt`, max 500 tokens per summary).

### 2d. Community Detection (Louvain)

GraphRAG runs Louvain community detection over the entity relationship graph to discover clusters of related entities. Hierarchical levels (0, 1, 2, …) are assigned.

### 2e. Community Summarization

Each community gets a summary report generated by the LLM (`prompts/community_report.txt`):
- `max_length: 2000` tokens per report
- `max_input_length: 8000` tokens of entity/relation context fed to the LLM

Community summaries are also embedded (3072-dim).

### 2f. Output Artifacts

GraphRAG writes Parquet files to `graphrag_workspace/output/`:

| File | Contents |
|------|----------|
| `entities.parquet` | Entity id, title, type, description, description_embedding, text_unit_ids |
| `relationships.parquet` | Source entity name, target entity name, description, weight |
| `text_units.parquet` | Chunk id, text, document_ids, entity_ids |
| `communities.parquet` | Community id, level, entity_ids |
| `community_reports.parquet` | Community integer key, title, summary, full_content, embedding |

## Stage 3 — Neo4j Import

**Code:** [scripts/import_to_neo4j.py](backend/scripts/import_to_neo4j.py)  
**Triggered automatically** after `graphrag index` succeeds.

### Stable Entity IDs

GraphRAG assigns new UUIDs on every index run, which would accumulate stale nodes across re-indexes. The import script computes a **deterministic stable ID** for each entity:

```python
stable_id = sha256(entity_name.upper().strip().encode()).hexdigest()[:32]
```

This ensures the same real-world entity (e.g., "Phòng Nhân Sự") maps to the same Neo4j node across every index run, even if GraphRAG issues a different UUID.

### Two-Phase Cleanup

Before importing, stale data is removed:

**Phase 1 — Transient nodes** (Community, TextUnit):  
Always deleted and recreated because their UUIDs change on every `graphrag index` run. Deleted in batches of 1000.

**Phase 2 — Stale entities**:  
Entity nodes whose stable ID is not present in the new Parquet are deleted. These represent entities from document sections that were removed or replaced. Entities shared across multiple documents survive because their stable ID appears in the new Parquet (contributed by the other documents).

### Import Order

```
1. Schema constraints + regular indexes (UNIQUE on id, INDEX on name/type/level/document_id)
2. Entity nodes        — MERGE on stable_id; SET name, type, description, embedding
3. Relationships       — MERGE RELATED_TO edges between Entity pairs
4. Community nodes     — MERGE on community UUID; SET level, title, summary, embedding
5. IN_COMMUNITY edges  — Entity → Community (uuid_to_stable mapping resolves graphrag UUIDs)
6. TextUnit nodes      — CREATE fresh (no MERGE — UUIDs always new)
7. MENTIONS edges      — TextUnit → Entity (via stable entity ID from entity.text_unit_ids)
8. Vector indexes      — cosine similarity on Entity.embedding and Community.embedding
```

All MERGE operations run in batches of 500 rows per transaction.

### Neo4j Schema After Import

```
(TextUnit)-[:MENTIONS]->(Entity)-[:RELATED_TO]->(Entity)
(Entity)-[:IN_COMMUNITY]->(Community)
```

Vector indexes:
- `entity_embedding` — cosine similarity on `Entity.embedding` (3072-dim by default)
- `community_embedding` — cosine similarity on `Community.embedding`

## Stage 4 — GraphRAG Service Reload

**Code:** [graphrag_service.py](backend/app/services/graphrag_service.py)

After Neo4j import completes, `GraphRAGService.reload()` is called. It reads all Parquet files into in-memory Pandas DataFrames under a `asyncio.Lock()` to prevent concurrent reloads. Once loaded, `is_ready = True` and both `local_search` and `global_search` become available.

---

## Re-indexing

When documents are updated and re-ingested:
1. New `.txt` files overwrite existing ones in `graphrag_workspace/input/`.
2. Trigger `POST /api/v1/admin/index` again (or pass `reimport: true`).
3. The two-phase cleanup in `import_to_neo4j.py` handles stale node removal automatically.

**Caution:** if the embedding model changes between runs, the vector index dimensions change and all existing embeddings become incompatible. Delete `graphrag_workspace/output/` and wipe the Neo4j graph before re-indexing with a new model.
